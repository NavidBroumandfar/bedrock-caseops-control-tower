# Production Readiness

Last updated: 2026-06-07

This checklist defines the minimum evidence required before treating a CaseOps
deployment as release-ready. The current architecture remains custom Python
orchestration on Lambda, not native Amazon Bedrock Agents.

## Current Production State

As of 2026-06-07, production infrastructure is deployed and one synthetic
production canary has passed in the maintainer's AWS account. Real production
traffic has not been launched. Public docs intentionally use sanitized resource
names and placeholders instead of account-specific identifiers.

| Field | Value |
|---|---|
| Production stack | `bedrock-caseops-control-tower-production` |
| Production function | `caseops-pipeline-production` |
| Production Knowledge Base | Bring-your-own `PRODUCTION_BEDROCK_KB_ID` |
| Production data source | Bring-your-own Bedrock KB data source |
| Production vector index | Bring-your-own vector index |
| Production output bucket | Generated by SAM in the target account |
| Guardrail ID / version | Bring-your-own Guardrail ID / version |
| Synthetic production canaries run | `1` |
| `production_traffic_launched` | `false` |

The current project stop condition is a no-traffic production freeze. A real
traffic launch should be treated as a new explicit operating decision, not as
remaining implementation work.

## Required Release Gate

Run these checks for the target environment.

1. Local tests pass:

```bash
python3 -m pytest -q
```

2. Deployment preflight passes:

```bash
python3 scripts/deployment_preflight.py
```

3. Stack deploys cleanly:

```bash
python3 scripts/deploy_stack.py --environment staging
```

4. Lambda allow-path invocation succeeds:

```bash
aws lambda invoke \
  --function-name caseops-pipeline-staging \
  --region "$AWS_REGION" \
  --payload fileb://events/lambda-inline-example.json \
  outputs/staging-lambda-response.json
```

5. Operational validation passes:

```bash
python3 scripts/operational_check.py \
  --stack-name bedrock-caseops-control-tower-staging \
  --region "$AWS_REGION" \
  --response-file outputs/staging-lambda-response.json
```

6. Guardrails block-path invocation returns `statusCode: 422` and
   `safety_status: "block"` with `guardrail_intervention`.

7. CloudWatch contains:

- Lambda service logs under `/aws/lambda/caseops-pipeline-{environment}`.
- Structured pipeline logs under `/caseops/pipeline/{environment}`.
- Metric filters for safety blocks, application errors, and archive failures.
- Alarms for Lambda errors, throttles, duration, safety blocks, application
  errors, and archive failures.

8. The final `CaseOutput` archive exists in the stack output bucket under:

```text
outputs/{document_id}/case_output.json
```

## Environment Isolation

Dev and staging must use separate CloudFormation stacks, Lambda functions,
document buckets, output buckets, log groups, and `CASEOPS_ENVIRONMENT`
dimensions.

Staging should use a separate Knowledge Base and vector index. The Phase 10
staging validation used isolated resources. Public-safe shape:

| Field | Value |
|---|---|
| Staging stack | `bedrock-caseops-control-tower-staging` |
| Staging function | `caseops-pipeline-staging` |
| Staging Knowledge Base | Separate from dev and production |
| Staging data source | Separate from dev and production |
| Staging vector index | Separate from dev and production |
| Guardrail ID | Bring-your-own Guardrail ID |
| Guardrail version | Bring-your-own Guardrail version |

## Rollback

To roll back an application stack update, redeploy the previous code revision
with the same deployment helper and environment parameters.

To remove the staging application stack:

```bash
aws cloudformation delete-stack \
  --stack-name bedrock-caseops-control-tower-staging \
  --region "$AWS_REGION"
```

## Cleanup

Only run cleanup commands when the corresponding environment is no longer
needed.

Delete the staging Knowledge Base data source and Knowledge Base:

```bash
aws bedrock-agent delete-data-source \
  --knowledge-base-id YOUR_STAGING_KB_ID \
  --data-source-id YOUR_STAGING_DATA_SOURCE_ID \
  --region "$AWS_REGION"

aws bedrock-agent delete-knowledge-base \
  --knowledge-base-id YOUR_STAGING_KB_ID \
  --region "$AWS_REGION"
```

If you changed a KB role S3 Vectors policy while creating staging resources,
restore the previous policy version before deleting the staging vector index:

```bash
aws iam set-default-policy-version \
  --policy-arn YOUR_KB_S3_VECTORS_POLICY_ARN \
  --version-id YOUR_PREVIOUS_POLICY_VERSION

aws iam delete-policy-version \
  --policy-arn YOUR_KB_S3_VECTORS_POLICY_ARN \
  --version-id YOUR_TEMPORARY_POLICY_VERSION
```

Delete the staging vector index:

```bash
aws s3vectors delete-index \
  --vector-bucket-name YOUR_VECTOR_BUCKET_NAME \
  --index-name YOUR_STAGING_VECTOR_INDEX_NAME \
  --region "$AWS_REGION"
```

Delete the Guardrail when it is no longer needed:

```bash
aws bedrock delete-guardrail \
  --guardrail-identifier YOUR_GUARDRAIL_ID \
  --region "$AWS_REGION"
```
